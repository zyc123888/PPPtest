# OmniTest 用例生成2

> 状态：已实现，持续优化  
> 功能入口：`/case/generator2`  
> 规则方案：`claw_5skill_unified`  
> 最后更新：2026-07-20

## 1. 功能定位

“用例生成2”是统一 Skill 方案的用例生成流水线，同时提供轻量模式和可信模式：

- **轻量模式**：保持接近原“用例生成”的快速生成体验；
- **可信模式**：先确定测试范围和证据，再生成可追溯用例，并通过多层门禁判断是否可以作为可信交付物。

V2 的重点不是单纯增加用例数量，而是回答以下问题：

1. 需求中有哪些直接测试对象？
2. 每个功能点来自哪段文字或哪张图片？
3. 每个 source 和功能点最终由哪些用例消费？
4. 是否存在遗漏、重复、旧状态误用、无依据断言或弱预期？
5. 最终 XMind 与结构化用例包是否一致？

V2 使用独立任务、attempt 和 artifact 数据，不修改原“用例生成”的历史任务。

## 2. 生成模式

| 页面模式 | API 值 | 历史兼容值 | 适用场景 |
|---|---|---|---|
| 轻量模式 | `lite` | `clone` | 快速生成 XMind、一般需求初稿、对强追溯要求不高 |
| 可信模式 | `trusted` | `trusted_v2` | 重要需求、长文档、图片需求、需要范围与证据审计 |

执行层会统一规范化历史值：

```text
clone      -> lite
trusted_v2 -> trusted
lite       -> lite
trusted    -> trusted
```

## 3. 可信生成策略

可信模式提供两种策略：

### 3.1 按 source 分片

这是完整可信生成路径。

- 建立 SourceManifest、证据追踪和范围索引；
- 每个 source 绑定功能点、适用测试方法和 `must_cover`；
- 按 source/shard 生成用例；
- 记录 source 和功能点消费回执；
- 支持失败 source shard 单独重跑；
- 经过需求门禁、用例门禁、语义复核和交付门禁。

适合正式交付和需要审计的任务。

### 3.2 轻量结果审查

这是快速预览路径。

- 复用轻量用例设计生成基线；
- 将轻量结果映射为可信结构和消费回执；
- 对结构、追溯和交付进行审查；
- 不执行完整的 source 分片设计。

它适合快速判断结果方向，不应与“按 source 分片”的可信强度等同。选择该策略后，页面不显示“生成密度”，因为密度参数只作用于 source 分片生成。

## 4. 生成密度

生成密度只在“可信模式 + 按 source 分片”时生效。

| 密度 | API 值 | 生成倾向 |
|---|---|---|
| 精简 | `concise` | 聚焦主流程和高风险点，允许合并低风险同构场景 |
| 均衡 | `balanced` | 覆盖核心、边界和关键异常，按风险控制合并 |
| 全面 | `exhaustive` | 展开权限、状态、组合和异常，仅合并完全重复场景 |

密度改变的是用例展开策略，不改变证据真实性、门禁规则和追溯要求。“全面”不代表无上限穷举，“精简”也不能省略 `must_cover`。

## 5. 用户输入

| 输入项 | 必填 | 说明 |
|---|---:|---|
| 所属项目 | 是 | 决定项目和工作空间归属 |
| 任务名称 | 是 | 用于任务展示和产物命名 |
| 生成模式 | 是 | 默认轻量模式 |
| 可信生成策略 | 可信模式 | 默认按 source 分片 |
| 生成密度 | source 分片 | 默认均衡 |
| 模型配置 | 是 | 使用保存配置或填写 API Key、模型和 Base URL |
| 需求来源 | 是 | 粘贴文本、上传文档、需求链接 |
| 需求正文 | 是 | 粘贴或上传时至少 10 个字符 |
| 导出 XMind | 默认开启 | 当前固定开启 |

上传文件支持 `.md`、`.markdown` 和 `.txt`，由浏览器读取文本后提交。

## 6. 页面进度与内部阶段

为避免 11 个节点挤压页面，可信模式在页面上合并显示为 5 个阶段；点击阶段可查看对应内部节点和中间产物。

| 页面阶段 | 内部阶段 | 具体工作 |
|---|---|---|
| 准备 | `orchestrate`、`evidence_trace` | 任务编排、收集正文和图片、建立 SourceManifest 与证据追踪 |
| 分析 | `scope_index`、`scope_index_gate`、`requirement`、`requirement_gate` | 建立直接测试对象范围、执行范围门禁、提取功能点、执行需求门禁 |
| 生成 | `testcase_by_source_shard`、`testcase_gate` | 生成或复用用例基线，建立消费回执，执行用例门禁 |
| 复核 | `quality_review` | 检查语义一致性、重复、弱预期、方法消费和无依据断言 |
| 交付 | `export`、`final_delivery_gate` | 生成 Markdown/XMindMark/XMind，并执行最终交付校验 |

轻量模式继续展示 6 个节点：收集、识图、分析、设计、评审、导出。

## 7. 可信模式详细流程

### 7.1 任务编排与证据追踪

- 解析需求章节、图片链接和正文规模；
- 对长文档选择完整或分批策略；
- 建立 `SourceManifest.json`，为文本与图片证据分配稳定标识；
- 生成 `EvidenceTrace.json`；
- 检查证据是否缺失、重复或无法绑定。

### 7.2 范围索引

`scope_index.json` 识别直接测试对象，而不是机械地把每个标题都当成功能：

- `source_id` 和标题；
- 主章节、依赖章节和规则簇；
- 当前状态与目标状态证据；
- 复杂度；
- 适用测试方法；
- `must_cover`；
- 用例预算和风险。

长文档可能按章节分批生成索引后合并。该提示表示采用了动态长文档策略，不等于范围门禁失败。

### 7.3 范围门禁

范围门禁检查：

- source 是否完整且标识唯一；
- 证据引用是否存在；
- 依赖、规则和图片是否正确绑定；
- target 目标状态是否与 current 旧状态区分；
- 预算、适用方法和 `must_cover` 是否存在；
- 分批合并后是否出现遗漏或冲突。

### 7.4 需求分析与需求门禁

需求分析把每个功能点绑定到 `source_id` 和原始证据。需求门禁检查：

- 功能点是否缺少 source；
- 是否只描述改造前状态而没有目标证据；
- 精确验收值是否丢失；
- source 是否已消费、合并、阻塞或判定不适用；
- 待确认项是否有真实问题文本；
- 数据结构是否符合 schema。

### 7.5 用例基线与用例门禁

按 source 分片时，每个 shard 独立生成并校验：

- 只使用绑定到当前 source 的证据；
- 消费适用测试方法和 `must_cover`；
- 生成步骤、测试数据、预期和 source 引用；
- 记录 `feature_point_consumption`；
- 控制密度、预算和同构合并；
- 校验 target 状态，禁止把 current 旧状态写成正向预期。

所有 shard 合并后执行全局用例门禁，检查遗漏、重复、超预算、未消费功能点、无依据文本和结构问题。

### 7.6 质量复核

质量复核结合确定性检查与模型语义审查：

- 功能点和 source 追溯完整性；
- 测试方法覆盖；
- 重复或同构用例；
- 弱预期与不可观察预期；
- 需求原文之外的断言；
- current/target 冲突；
- 精确数值、位置、状态和权限规则是否保留。

模型审查不能替代后端硬校验；确定性门禁也不能完全理解语义，两者共同构成当前可信判断。

### 7.7 导出与交付门禁

V2 从最终结构化用例包确定性生成 XMindMark 和 XMind。交付门禁至少检查：

- XMindMark 和 XMind 产物存在；
- XMindMark 无空行、缩进合法、第一行是根节点；
- 可信模式包含 `SRC-` 追溯节点；
- XMindMark 的 `TC-` 数量与用例包一致；
- review summary 的用例数与用例包一致；
- Source、功能点、用例消费与结构统计一致；
- 语义审查达到可信交付要求；
- 无超阈值的无依据断言、精确值丢失、弱预期等阻断问题；
- trusted 硬校验器可用并通过。

门禁失败时，任务状态为 `FAILED` 或不可可信交付。即使磁盘上已经生成 XMind，也不能把它作为通过门禁的最终结果。

| 阶段 | 产物 | 用途 |

| 准备 | `SourceManifest.json` | 统一登记文本、章节、图片和证据标识 |

| 生成 | `trusted_testcase_package.json` | 最终结构化用例包 |
| 生成 | `testcase_handoff.json` | 功能点消费、source 统计和 shard 状态 |
| 生成 | 用例门禁报告 | 检查覆盖、方法、预算和结构 |

## 9. 可信指标

页面根据真实产物展示，不用单一“100% 覆盖率”替代全部质量判断。主要指标包括：

- 直接测试对象数；
- 功能点数；
- 实际用例数；
- Source 有用例率；
- Source 追溯完整率；
- 功能点回执完整率；
- 合并覆盖数；
- 重复用例数和重复率；
- 弱预期率；
- 待确认数量；
- 超预算 source 数；
- 模型调用次数、Token 和总耗时；
- 与可比 V1 任务的指标差异。

这些指标分别描述结构、消费和质量，不应解释为“业务需求已被 100% 正确理解”。

## 10. 缓存、并发与长文档

### 10.1 复用

重跑时，系统会判断已经通过门禁且输入仍兼容的产物是否可复用，包括范围索引、需求分析和已通过的 source shard。复用可以显著缩短任务时间，因此同一任务重跑从几十分钟降到几分钟可能是正常现象。

### 10.2 分批与并发

- 文档规模超过阈值时，范围索引和需求分析可按章节分批生成后合并；
- source shard 可在受控并发下生成；
- 并发受模型配额、超时和 Worker 资源限制；
- 系统不会为追求速度而静默生成 Python 占位结果。

### 10.3 复用边界

以下变化应使相关产物失效或重新生成：

- 需求正文、图片或目标状态证据变化；
- 模式、可信策略或生成密度变化；
- schema、规则版本或关键 Prompt 变化；
- 上游门禁结果变化；
- source/function point 标识发生不兼容变化。

## 11. 页面操作

### 11.1 最近任务

- 支持按模式和状态筛选；
- 显示模式、状态、用例数量和摘要；
- 进行中任务固定在顶部；
- 历史 `clone/trusted_v2` 任务按轻量/可信模式展示。

### 11.2 结果详情

- 显示模式、策略、密度、索引策略、状态和错误；
- 显示真实运行指标和 V1 对比；
- 显示 5 个合并进度阶段及内部节点；
- 点击阶段查看对应中间产物；
- 下载最终 XMind 或单个 JSON/Markdown 产物；
- 查看 gate 问题、恢复建议和 source 明细。

### 11.3 恢复操作

- **重跑任务**：沿用原输入和模式，刷新最新模型配置；
- **停止任务**：撤销当前 attempt 并更新为 `CANCELLED`；
- **重跑 source shard**：只重跑失败或需修复的 source，再从用例门禁继续；
- **刷新详情**：读取最新心跳、阶段、attempt 和产物。

同一用户已有进行中任务时，页面阻止再次创建新任务。

## 12. 任务状态和可信语义

| 状态 | 含义 |
|---|---|
| `PENDING` | 等待 Worker |
| `RUNNING` | 正在执行 |
| `SUCCESS` | 流程完成且达到对应模式的成功条件 |
| `CONDITIONAL` | 已完成但存在需要人工复核的风险 |
| `FAILED` | 模型、结构、阶段门禁或交付门禁失败 |
| `CANCELLED` | 用户已停止 |

“生成完成”“XMind 已存在”和“可信交付通过”是三个不同概念。可信模式只有最终交付门禁通过后，才可以声明为可信交付物。

## 13. 常见失败与处理

| 错误 | 含义 | 建议 |
|---|---|---|
| 模型 JSON 不完整 | 响应被 `max_tokens`、模型中断或超时截断 | 重跑失败阶段；检查模型稳定性 |
| source shard 失败 | 当前 source 的证据、方法或 must_cover 未满足 | 查看 source 问题并单独重跑 shard |
| FP 未出现在消费回执 | 功能点没有被覆盖、合并或阻塞说明 | 重跑用例阶段 |
| current 与 target 冲突 | 用例把改造前状态当成目标预期 | 修复上游证据绑定后重跑 |
| 文本依据不在原文 | 模型生成了无依据断言 | 重跑 shard 或转为待确认 |
| 待确认项显示 `-` | 数据只有占位符，或旧 XMind 未重新导出 | 修复后重新导出；必要时重跑 |
| 交付门禁缺少硬校验器 | 容器规则目录或挂载不完整 | 检查 unified/final 工具目录并重启 Worker |
| 长时间无进展 | Worker 中断、任务失去活跃执行或模型长时间无响应 | 检查容器和 Worker，再重跑 |

## 14. 当前限制与风险

- 完整可信模式模型调用较多，首次运行成本和耗时高于轻量模式。
- 模型服务的 5xx、配额和上下文限制仍会影响 shard 成功率。
- 可信模式降低遗漏风险，但不能证明需求文档本身完整或正确。
- 分批分析可能丢失跨章节语义，合并门禁只能降低、不能彻底消除该风险。
- “轻量结果审查”是快速预览，不等于完整 source 分片生成。
- 中间产物和门禁较多，规则变更必须同步更新 schema、加载器、前端映射和本文档。

## 15. 与原版的选择建议

| 情况 | 建议 |
|---|---|
| 快速得到一般需求的 XMind 初稿 | 原“用例生成”或 V2 轻量模式 |
| 重要版本、验收要求严格 | V2 可信模式 + 按 source 分片 |
| 长手册、多图片、跨章节规则 | V2 可信模式，接受更长首次耗时 |
| 只想快速观察可信结构是否合理 | V2 可信模式 + 轻量结果审查 |
| 只修复某个失败模块 | V2 source shard 重跑 |

## 16. 维护规则

以后修改“用例生成2”时，必须同步更新本文档：

1. 模式、策略、密度或兼容映射变化；
2. 页面 5 阶段或内部阶段发生增删、合并、重命名；
3. SourceManifest、schema、消费回执或 artifact 结构变化；
4. 门禁阈值、阻断语义、模型审查或硬校验器变化；
5. 缓存、复用、分批、并发或 shard 重跑策略变化；
6. 可信指标、统计口径、V1 对比逻辑变化；
7. XMind 结构、下载行为、任务状态或恢复操作变化。

规划功能不得写成已实现。新增功能合并代码时，文档更新应作为同一变更的一部分提交。

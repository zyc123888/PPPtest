# 用例生成任务 #10 评估与优化建议

> 任务：`#10 新验证`
> 需求文档：`DSP - DSP平台整体交互优化.md`
> 当前结论：`有条件通过`
> 评估依据：
> - `backend/reports/case_generation/job_10/review_report.json`
> - `backend/reports/case_generation/job_10/DSP - DSP平台整体交互优化.xmind`

## 1. 总体判断

这批产物已经不是“堆数量的空泛用例”，整体结构比较完整：

- 已按 `模块 -> 场景 -> 功能点 -> 用例` 组织导图
- 功能点覆盖完整，`29/29` 已覆盖
- 标题大多能贴住需求点，主流程、边界、异常、UI 交互都有体现

但它目前更像“可评审初稿”，还不能算“可直接执行交付件”。

核心原因不是用例数量不够，而是下面三类问题仍然明显存在：

1. 需求边界未闭环
2. 预期与步骤的可执行性不足
3. 生成后审计口径不一致，降低结果可信度

## 2. 必须改

### 2.1 先闭环待确认项，再执行相关用例

`review_report.json` 中证据链状态是 `incomplete`，且有 6 个 `pending_confirmations`。

其中影响最大的不是“截图缺失”本身，而是会直接改变用例判定标准的业务边界：

- `More Filters` 哪些字段属于一级菜单，哪些字段属于二级菜单
- `SubAccount -> Account` 是全局改名，还是仅限特定模块
- `ID支持` 里的搜索前缀展示形式未明确

这些问题未确认前，以下类型用例都存在“测了但标准不稳”的风险：

- 字段隔离类用例
- 全局回归类用例
- 文案改名类用例
- UI 布局对照类用例

建议动作：

- 先产出一份待确认清单给产品/业务确认
- 确认后回刷 `FunctionPoints`
- 仅对受影响模块重生成/重审

### 2.2 修复“猜测型预期”

部分用例把模型自己的合理猜测写进了预期，而不是严格承接需求。

典型例子：

- `TC-005-003` 预期写成“按常规多选 OR 验证”，同时又承认实际 `AND/OR` 逻辑未明确

这类用例的问题是：

- 看起来完整
- 实际上把未确认规则伪装成了可执行标准
- 执行人员容易误把“模型猜测”当成“需求结论”

建议动作：

- 对所有含“按常规”“通常”“若无明确说明则”这类表述的预期做一次专项扫描
- 未确认规则统一降级为“待确认后执行”或拆成两个候选用例

### 2.3 修复步骤与预期不对齐

`review_report.json` 已指出 4 条典型问题用例：

- `TC-003-003`
- `TC-003-004`
- `TC-004-003`
- `TC-004-004`

这些用例的共同问题是：

- 预期要求验证“后端接口参数传递正确”
- 步骤只写“输入条件后点击 Search 验证结果”
- 没有说明如何抓包、看请求参数、核对 payload

这会让纯 UI 执行人员无法稳定复现同样的验证动作。

建议动作：

- 凡是预期涉及“接口参数正确 / 请求字段正确 / payload 正确”的用例
- 步骤中必须明确加入：
  - 打开浏览器开发者工具
  - 定位目标请求
  - 核对请求参数字段

如果不准备让这类用例承担接口校验职责，就应删掉相关预期，只保留 UI 可观察结果。

### 2.4 修复统计口径不一致问题

这批结果里，审计数字前后不一致：

- `summary.testcase_count = 94`
- `execution_proof.summary_lines` 里也是 `94`
- 但 `case_count = 96`
- `quality_summary.case_count = 96`
- 导图统计信息里也是 `96`

这类问题虽然不直接影响单条用例执行，但会明显影响平台可信度，后续会连带污染：

- 生成质量评估
- 版本对比
- 评审通过率
- 基线数量统计

建议动作：

- 明确唯一计数口径：是去重前、去重后，还是导出后最终数量
- 在生成链路里统一使用同一份最终计数结果回填所有 summary 字段
- 增加回归校验：`summary.testcase_count == case_count == quality_summary.case_count`

## 3. 建议改

### 3.1 收紧弱预期和弱步骤

当前审查结果里：

- `weak_expected_count = 45`
- `weak_step_count = 40`

这说明虽然大多数用例“长得像用例”，但还有不少条目缺少真正可复核的判定点。

当前常见弱化模式包括：

- “页面正常展示”
- “交互正常”
- “返回正确数据”
- “不报错”

这类预期建议改成可观察对象：

- 具体文案
- 字段值
- 控件状态
- 列表条数
- 请求参数
- 导出文件列名

### 3.2 控制 P0 的使用边界

这批一共 `15` 条 `P0`，不算离谱，但有些条目已经带出“偏 UI 但优先级很高”的倾向。

例如改名类、统一展示类、全局消失类，很容易被模型推成高优先级。这里需要更明确的打标原则：

- 直接影响主流程不可用：`P0`
- 影响主要功能正确性：`P1`
- 展示一致性、样式、可用性细节：优先 `P2`

建议后续把优先级规则再显式喂给 `testcase-designer`，减少“名称统一类用例天然高优”的漂移。

### 3.3 给“全局回归”类用例补检查范围清单

像 `TC-018-002` 这种“全局彻底消失”用例，问题不是不该有，而是范围太泛。

当前步骤是：

- 遍历 `Report / Campaign / Ad Set` 等相关模块
- 检查是否还有 `SubAccount`

这会带来两个问题：

1. 执行人理解范围不一致
2. 回归结果无法稳定复核

建议动作：

- 全局回归类用例必须带“检查清单”
- 清单可来自需求章节、模块枚举或导出面板列表

## 4. 可后置

### 4.1 决策表覆盖补强

`review_report.json` 已指出：

- `decision_table = missing`

这一点主要集中在：

- `CPI/ROI`
- `Deep Action Optimize`
- 枚举项归属和移除逻辑

这类问题短期不一定会挡住交付，但会影响后续复杂配置场景的漏测率。

建议后续新增一类组合场景用例：

- 出价类型
- 是否显示某按钮
- 某模块是否移除
- 枚举归属分类

按表驱动生成，不要只靠单点增删验证。

### 4.2 角色与环境维度补齐

当前审查结果里：

- `role = partial`
- `environment = partial`

说明这批更偏单环境、单角色主线验证。

这对当前需求不一定是致命问题，但如果后续你想把这套能力作为平台卖点，建议慢慢补两类能力：

- 不同角色可见性 / 可操作性差异
- 不同分辨率、浏览器、语言环境下的稳定性差异

## 5. 建议的落地顺序

### 第一阶段：先把结果变得“可信”

1. 修统计口径不一致
2. 闭环 6 个待确认项
3. 修正“猜测型预期”

### 第二阶段：再把结果变得“可执行”

1. 修复抓包类步骤缺失
2. 给全局回归类用例补范围清单
3. 收紧弱预期和弱步骤

### 第三阶段：最后做“质量增强”

1. 补决策表
2. 补角色矩阵
3. 补环境维度

## 6. 最终结论

如果按当前状态评估：

- 作为“生成初稿”是合格的
- 作为“可直接执行的正式测试资产”还差一轮收口

更准确地说，`#10` 的问题不在于“生成得不够多”，而在于：

- 有一部分用例还在替需求做猜测
- 有一部分用例还没有把验证动作写实
- 平台对最终统计结果的回填还不够一致

所以后续优化方向不该继续偏向“多生成几条”，而应该优先做：

1. 边界闭环
2. 预期去猜测化
3. 步骤可执行化
4. 审计口径统一化

# 用例生成性能优化 —— 风险评估文档（Document A）

> 范围：`backend/app/tasks/case_generation.py` 用例生成流水线性能优化
> 状态：**仅评估，未改动任何代码**
> 结论摘要：A 档（纯配置）风险低；B 档（小改代码）风险中；C 档（架构级）风险高，可能显著改变产出质量与稳定性。

---

## 0. 风险等级说明

| 等级 | 含义 |
|------|------|
| 🟢 低 | 可随时回滚，不改变产出结构，最坏只是退回原状 |
| 🟡 中 | 改动核心逻辑，可能影响用例数量/质量，需回归验证 |
| 🔴 高 | 改变流水线结构或质量门禁，可能产生难以察觉的质量退化 |

---

## A 档：配置调整（纯 `.env` 覆盖，不动源码）

### A1. `CASE_GEN_TESTCASE_REPAIR_MAX_ROUNDS` 2 → 1
- **改动**：审查 → 修复 → 复审循环从 2 轮降为 1 轮。
- **风险等级**：🟡 中
- **风险点**：
  - 减少一轮修复，**部分功能点的用例覆盖率/密度可能在第 1 轮未补齐**。
  - 代码中存在硬门禁：`_gate(not missing_ids, ...)`（覆盖未达标直接抛错）、`_gate(not insufficient, ...)`（密度不足抛错）。轮数减少后，**若一轮补不齐，任务会直接 FAILED**，而不是变慢。
  - 即"由慢变成失败"的风险，比单纯变慢更需要关注。
- **影响面**：所有需求复杂、功能点多的任务。简单需求基本无影响。
- **触发条件**：单批生成质量不稳定、模型偶发漏覆盖时。
- **回滚**：改回环境变量即可，秒级。

### A2. `CASE_GEN_MAX_CONCURRENCY` 4 → 8（或更高）
- **改动**：`_gather_limited` 的并发上限提升。
- **风险等级**：🟡 中
- **风险点**：
  - **模型供应商 QPS / TPM 限流**：并发翻倍后更易触发 HTTP 429，而 429 会进入重试逻辑（`_MAX_AI_RETRIES`），**反而可能更慢甚至失败**。
  - 同时打满图片识别 + 需求分析 + 用例设计的批次，瞬时请求峰值变高。
  - 后端进程内存/连接数上升（每个并发当前都新建 `httpx.AsyncClient`）。
- **影响面**：全局所有阶段。
- **触发条件**：模型账号有严格限流；批次数量大。
- **回滚**：改回环境变量；建议先小步到 6 观察限流日志。

### A3. `CASE_GEN_MAX_AI_RETRIES` 2 → 1
- **改动**：每个 AI 调用的最大重试次数减少。
- **风险等级**：🟡 中
- **风险点**：
  - 模型**偶发**返回截断 JSON / 校验不过时，原本第 2 次重试能救回的，现在会直接判失败。
  - 与 A2 叠加（并发高→易限流→更需要重试）时，**任务失败率可能明显上升**。
- **影响面**：所有 AI 调用阶段。
- **触发条件**：模型输出不稳定、网络抖动、限流。
- **回滚**：环境变量改回。

### A4. `CASE_GEN_MIN_CASES_PER_FUNCTION_POINT` 5 → 3
- **改动**：每个功能点最少用例数下调。
- **风险等级**：🔴 高（业务影响，非技术风险）
- **风险点**：
  - **直接减少最终交付的用例数量**，是对外可见的产出变化，需业务方明确同意。
  - 影响 `target_case_count_for_fp`、`supplement_case_density`、密度门禁 `insufficient` 判定。
  - 高变化功能点（含筛选/分页/搜索等）仍硬编码为 5（`return 5 if ...`），该项只影响普通功能点。
- **影响面**：所有产出的用例总量与覆盖深度。
- **触发条件**：每次生成。
- **回滚**：环境变量改回；但已生成的历史产物不会追溯补齐。

## B 档：小改代码（收益高，风险中）

### B1. quality-reviewer 输入数据压缩
- **改动**：审查阶段（`_build_review_report`）对 `function_points` / `testcase_package` 做裁剪后再传给模型（目前是全量塞入）。
- **风险等级**：🟡 中
- **风险点**：
  - **审查是质量门禁**，裁剪掉的字段若恰好是审查判断依据，可能导致**误判 pass 或误判 fail**。
  - 误判 pass：质量退化但流程放行（最危险，难察觉）。
  - 误判 fail：触发不必要的修复循环，**反而更慢**。
  - 审查 prompt 里要求输出 `coverage.uncovered_fp_ids` 等，裁剪后模型可能拿不到全量 fp 列表，影响覆盖率判断。
- **影响面**：质量审查结论的准确性。
- **触发条件**：裁剪策略与审查关注点不匹配时。
- **回滚**：保留原函数，开关切换；需对比裁剪前后审查结论一致性。

### B2. 复审增量化（只复审被改动/曾 fail 的功能点）
- **改动**：修复后不再全量重审，只审增量。
- **风险等级**：🔴 高
- **风险点**：
  - 修复某功能点的用例时，**可能影响全局统计**（优先级分布、去重、编号 `renumber_cases`），增量审查会**漏掉这些跨功能点副作用**。
  - 现有审查含全局校验（如 `coverage`、`dimension_matrix`），增量化需要重新设计聚合逻辑，**容易引入不一致**。
- **影响面**：最终审查结论的完整性。
- **触发条件**：修复引入跨功能点影响时。
- **回滚**：逻辑分支保留全量审查兜底。

### B3. 共享 httpx 连接池 + 合并事件循环
- **改动**：用单一 `AsyncClient`（带连接池）贯穿全流程，减少各阶段 `asyncio.run()` 重复建销。
- **风险等级**：🟡 中
- **风险点**：
  - 当前每阶段独立 `asyncio.run()` 是**强隔离**，合并后若某阶段异常，可能影响共享 client 生命周期。
  - 运行在 **Celery worker** 中，事件循环与 client 的生命周期管理需与 worker 模型兼容，处理不当会出现 "event loop closed" / client 复用跨任务污染。
  - 连接池跨任务复用需确认无状态泄漏（API Key、base_url 不同任务不同）。
- **影响面**：所有 AI 调用的底层网络层。
- **触发条件**：异常路径、并发任务、worker 复用进程。
- **回滚**：封装在调用层，可切回每次新建 client。

### B4. 抽取类调用关闭 `<thinking>`（需求分析 / 用例设计）
- **改动**：去掉 system prompt 中"先在 `<thinking>` 标签深度分析"的要求，仅保留审查阶段思考。
- **风险等级**：🟡 中
- **风险点**：
  - **可能直接降低用例质量**：thinking 对"结合需求生成具体步骤/预期"有实际帮助，去掉后模板化内容可能增多。
  - 代码里有大量反模板门禁（`_GENERIC_*_PATTERNS`、`_gate(... 过于模板化)`），质量一降可能**触发更多门禁失败 → 重试 → 反而更慢**。
  - `_json_from_model_text` 会剥离 thinking，去掉后解析逻辑无碍，但质量是主要顾虑。
- **影响面**：需求分析、用例设计两阶段的产出质量。
- **触发条件**：每次生成。
- **回滚**：prompt 文本改回；建议做 A/B 质量抽样对比后再定。

## C 档：架构级改造（收益最大，风险最高）

### C1. 阶段流水线化（需求分析与用例设计重叠执行）
- **改动**：功能点一产出即进入用例设计，打破"阶段 4 全部完成才进阶段 5"的屏障。
- **风险等级**：🔴 高
- **风险点**：
  - 现有逻辑大量依赖**全量 function_points**：`_assign_requirement_groups`、`renumber_cases`、密度/覆盖门禁、XMind 分组都按完整集合计算。流式化会**打乱全局编号与分组**。
  - 错误处理复杂度陡增：部分功能点失败时的回滚/补齐语义需重新定义。
  - 改动面广，**回归测试成本高**，潜在 bug 难定位。
- **影响面**：整条流水线的执行模型与产出结构。
- **触发条件**：每次生成。
- **回滚**：需保留旧路径作为开关，改造工作量大。

### C2. 新增"快速模式"开关（跳过审查-修复循环）
- **改动**：提供快/精双模式，快速模式只生成一次 + 轻量校验。
- **风险等级**：🔴 高
- **风险点**：
  - 快速模式**绕过质量门禁**，产出质量无保障，需明确标注并与用户达成预期。
  - 两套路径长期维护成本，易出现"只改了一条路径"的不一致 bug。
  - 若默认值设错（误用快速模式做正式交付），影响交付质量。
- **影响面**：产出质量与交付可信度。
- **触发条件**：用户选择快速模式 / 默认配置错误。
- **回滚**：保留精确模式为默认即可。

## 总体建议与风险对冲

1. **先 A 档、单项灰度**：一次只调一个参数并实测耗时与失败率，避免多变量叠加（尤其 A2+A3 叠加会放大失败率）。
2. **A1/A3/A4 都有"由慢变失败"或"由慢变质量下降"的转化风险**，不是纯加速，需配套监控任务失败率与用例数量。
3. **B 档需要质量回归基线**：改前先固定几个代表性需求，记录用例数/覆盖率/审查结论作为基线，改后对比。
4. **C 档不建议在未建立自动化质量回归前实施**。
5. 任何改动建议保留 `backup_before_optimization/` 同款备份机制，便于回退。

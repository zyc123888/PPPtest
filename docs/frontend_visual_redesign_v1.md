# PPPtest 前端视觉改造方案 v1

## 1. 目标

本轮不是重做整站，也不是先做一套“很炫”的设计稿，而是以高可行性为原则，在不推翻现有 Vue + Element Plus 结构的前提下，把 PPPtest 从“可用后台”提升到“有产品感的测试平台”。

本方案优先解决三类问题：

1. 整站视觉语言不统一
2. 核心页面的信息层级太弱
3. 复杂业务页面像表单和表格的堆叠，缺少专业工具感

## 2. 当前问题诊断

### 2.1 整体观感为什么会显得“丑”

不是因为某一个按钮难看，而是几件事叠加：

1. 页面几乎都在重复 `标题 + 白卡片 + 筛选卡片 + 表格卡片`，结构过于单一。
2. 卡片、边框、表格很多，但“重点信息”没有被明显强调。
3. 标题区、操作区、筛选区、主体区的层次差异太小，页面显得平。
4. 全站色彩很克制，但缺少真正的视觉主轴，只有默认后台感，没有“测试平台感”。
5. 复杂页面已经有很多能力，但 UI 仍像管理后台，不像专业工具。

### 2.2 代码层面的现实约束

当前前端已经形成比较稳定的结构，适合做“增量产品化”，不适合全量推翻：

1. 全局页头和页面骨架统一，见 [frontend/src/components/PageHeader.vue](/Users/zhangyongcheng/Desktop/PPPtest/frontend/src/components/PageHeader.vue:1) 和 [frontend/src/layout/index.vue](/Users/zhangyongcheng/Desktop/PPPtest/frontend/src/layout/index.vue:1)
2. 全局 token 已经存在，但层级偏少，见 [frontend/src/styles/tokens.css](/Users/zhangyongcheng/Desktop/PPPtest/frontend/src/styles/tokens.css:1)
3. 大量页面已复用 `app-page / page-card / section-gap`，见 [frontend/src/styles/global.css](/Users/zhangyongcheng/Desktop/PPPtest/frontend/src/styles/global.css:1)
4. 侧边栏品牌和主体内容区有基础，但还没形成完整品牌系统，见 [frontend/src/layout/components/Sidebar.vue](/Users/zhangyongcheng/Desktop/PPPtest/frontend/src/layout/components/Sidebar.vue:1)

结论：适合先做一轮“设计系统补强 + 3 个核心页面重构”，而不是整站大换血。

## 3. v1 风格方向

## 3.1 风格关键词

- 专业
- 清晰
- 冷静
- 有分析感
- 不做通用后台模板感

## 3.2 建议的视觉定位

推荐走“测试平台 + 分析工具”的混合风格，而不是传统 ERP 后台风格。

参考组合：

1. Postman：接口编辑器和请求构建体验
2. Sentry：执行失败分析、详情页层级
3. Datadog / Grafana：工作台、趋势、状态可视化
4. Linear：列表、筛选、密度控制、克制感

## 3.3 不建议的方向

1. 不建议做彩色大面积渐变互联网官网风
2. 不建议做重拟物或过深阴影
3. 不建议全站继续依赖 Element Plus 默认视觉
4. 不建议每个页面单独发挥，必须先统一视觉骨架

## 4. v1 改造原则

## 4.1 先统一框架，再改单页

先改全局基础层，再改页面。否则每页都会各长各的。

优先顺序：

1. 设计 token 和全局容器
2. 顶部栏 / 侧边栏 / PageHeader
3. 工作台
4. 接口用例编辑器
5. 执行中心 / 报告中心

## 4.2 保持高可行性

本轮只做这些高性价比动作：

1. 扩充 CSS token，不改技术栈
2. 封装少量通用容器组件或样式类
3. 基于现有页面结构重排，而不是重建所有页面
4. 只挑最影响观感和产品感的页面做深改

## 5. 分阶段实施

## Phase 1：全局设计系统补强

### 目标

先把全站“底子”统一，让后续页面改造不会散。

### 改造内容

1. 扩充 token
   - 增加更细的 spacing：`4 / 8 / 12 / 16 / 20 / 24 / 32`
   - 增加 radius 层级：`8 / 12 / 16`
   - 增加 surface 分层：`page / card / elevated / muted`
   - 增加文本层级：`title / section / body / secondary / caption`
   - 增加状态色的浅底和边框色

2. 统一字体策略
   - 中文建议用 `Noto Sans SC` 或 `PingFang SC`
   - 数字和关键指标区可用 `Manrope`
   - 让当前已引入但未实际生效的字体真正落地

3. 统一页面骨架
   - 页面头部增加更清晰的标题层级
   - 页面内容区最大宽度、左右留白、区块间距统一
   - 筛选区和主内容区视觉区分更明显

4. 统一卡片规范
   - 弱化大面积边框感
   - 通过背景层、阴影和间距区分层级
   - 表格容器和信息卡片容器分成两类样式

### 预期收益

1. 整站立刻不再像默认后台
2. 后续页面改造成本下降
3. 视觉一致性显著提升

## Phase 2：全局导航与框架升级

### 目标

把“左侧菜单 + 顶部栏 + 标题区”做成真正的平台框架。

### 改造内容

1. 左侧导航
   - 强化品牌区，不再只是一行 logo 文字
   - 当前激活菜单做更明显高亮和区域包裹
   - 分组标题和业务模块区分更清楚
   - 收起态图标对齐和 hover 态统一

2. 顶部栏
   - 面包屑弱化
   - 增加全局搜索或命令入口占位
   - 状态标签从“前端在线”这种弱价值信息，改为更有意义的系统状态聚合

3. PageHeader
   - 标题、副标题、操作区重新定义节奏
   - 标题区可以支持状态说明、快捷入口、摘要指标

### 预期收益

1. 框架层产品感上来
2. 各页面之间不再显得只是换了一张表格

## Phase 3：工作台重做

### 目标

把工作台从“数字展示页”改成“测试运营驾驶舱”。

### 当前问题

1. 统计卡片只是数字罗列
2. 健康状态和执行记录都很平
3. 用户一进来不知道系统风险、失败热点和待处理项

### 改造方向

工作台分成四段：

1. 顶部概览
   - 今日执行数
   - 失败率
   - 待处理失败
   - 环境异常数

2. 风险焦点区
   - 最近失败最多的计划或用例
   - 最近异常环境
   - 待评审 / 待回归项

3. 趋势区
   - 最近 7 天执行趋势
   - 通过率趋势
   - 失败原因分布

4. 最近活动区
   - 最近执行记录
   - 最近报告
   - 最近变更

### 实施方式

1. 优先复用现有接口和已有数据聚合
2. 图表先做简单版，不上复杂图表库也可以先用轻量实现
3. 先保证“异常优先”而不是“所有数据都展示”

### 预期收益

1. 首页价值明显提升
2. 用户进入系统后更知道该做什么

## Phase 4：接口用例编辑器重做

### 目标

把“新增接口用例”从后台表单升级成 API Editor。

### 当前问题

1. 功能已经很多，但视觉仍像大表单
2. 请求配置区和元数据区没有明显分层
3. 即时调试、Body、Auth、Headers 这些核心能力还没形成工具感

### 改造方向

编辑弹窗改成三段式：

1. 顶部请求条
   - Method
   - URL / Path
   - Send
   - 环境切换

2. 中部编辑区
   - Params / Headers / Auth / Body / Assertions
   - 左右或上下分区更明确

3. 右侧或下方响应区
   - 状态码
   - 耗时
   - 响应头
   - 响应体
   - 实际请求

4. 元信息区折叠
   - 项目
   - 目录
   - 优先级
   - 标签
   - 评审
   - 版本

### v1 实施策略

不一步到位做完整双栏 IDE，而是先做：

1. 请求构建区高亮
2. Tabs 区重新排版
3. 调试区视觉升级
4. 元数据区降权

### 预期收益

1. 核心能力的专业感立刻提升
2. 这页会成为全站设计标杆页

## Phase 5：执行中心 / 报告中心分析化

### 目标

把“执行记录查看页”升级成“问题分析页”。

### 当前问题

1. 信息很多，但更像堆叠式查看
2. 失败原因、步骤、日志、产物之间关系不够清晰
3. 没有明显的“先看结论，再看证据”的结构

### 改造方向

1. 执行详情页
   - 顶部结论条：状态、耗时、环境、重试、失败摘要
   - 中部主证据：步骤、日志、错误摘要
   - 侧栏辅助信息：基础元数据、触发来源、执行配置

2. 报告中心
   - 列表页加入质量概览区
   - 详情页突出趋势、失败聚类、历史对比
   - 下载和原始数据入口弱化到次级区

### 预期收益

1. 页面更像 Sentry / 测试分析平台
2. 用户定位问题更快

## 11. 页面优先级打分表

为了避免后续靠感觉排期，建议对核心页面按四个维度打分：

- 业务价值：是否高频使用，是否影响主流程
- 视觉收益：改完后是否能明显提升整体观感
- 开发成本：实现复杂度和改动范围
- 依赖风险：是否依赖大量后端接口或联动逻辑

评分规则：

- 高 = 3
- 中 = 2
- 低 = 1

建议排序如下：

| 页面/模块 | 业务价值 | 视觉收益 | 开发成本 | 依赖风险 | 建议优先级 | 说明 |
|---|---:|---:|---:|---:|---:|---|
| 全局导航与框架 | 3 | 3 | 2 | 1 | P0 | 改动收益覆盖全站，是最划算的起点 |
| 工作台 | 3 | 3 | 2 | 2 | P0 | 首页感知最强，能快速拉高产品感 |
| 接口用例编辑器 | 3 | 3 | 3 | 2 | P0 | 这是最核心的专业能力页，值得深改 |
| 执行中心 | 3 | 2 | 2 | 2 | P1 | 已有功能较多，重排后收益明显 |
| 报告中心 | 3 | 2 | 3 | 2 | P1 | 更偏分析型页面，适合第二轮深改 |
| 用例中心 | 2 | 2 | 2 | 1 | P1 | 改完会更统一，但不是第一眼关键页 |
| 测试计划 | 2 | 2 | 2 | 2 | P1 | 主流程页，但现阶段不是视觉短板第一名 |
| 环境管理 / 项目管理 / 用户权限 | 2 | 1 | 1 | 1 | P2 | 这类管理页先跟随全局风格升级即可 |
| 常用工具 | 1 | 1 | 1 | 1 | P2 | 功能型页面，后置处理即可 |

建议的执行顺序不变：

1. 全局框架
2. 工作台
3. 接口用例编辑器
4. 执行中心
5. 报告中心

## 12. 视觉规范小样

这部分不是最终品牌手册，而是供开发时直接对照的轻量规则。

### 12.1 色彩方向

建议保留你现在偏冷静的青绿主色，但做成更完整的体系：

- 主色：青绿，用于主按钮、当前导航、高亮操作
- 强调色：蓝青，用于信息态、链接态、次级重点
- 风险色：红，用于失败、阻断、错误
- 警告色：琥珀，用于预警、待处理
- 成功色：绿，用于通过、健康

页面背景建议分三层：

1. 页面底色：很浅的灰蓝或灰白
2. 普通容器：纯白
3. 强调容器：轻微带色或轻阴影的白

### 12.2 卡片规范

卡片不再统一一刀切，而是分成三类：

1. 指标卡
   - 更强数字、较弱说明
   - 可带趋势或状态

2. 数据容器卡
   - 用于表格、列表
   - 弱边框，强调内部结构

3. 分析面板卡
   - 用于日志、趋势、失败分析
   - 更明确头部和内容区

### 12.3 表格规范

表格页面建议统一这些原则：

1. 表头背景轻微提亮，不要与正文无差别
2. 行高略加大，减少默认后台的压迫感
3. 操作列按钮分主次，不要所有操作权重一样
4. 重要状态用 `StatusPill` 展示，而不是纯文本
5. 表格上方的筛选区要与表格主体明确分离

### 12.4 标签和状态规范

状态标签建议分为：

1. 结果态：成功 / 失败 / 取消 / 进行中
2. 流程态：DRAFT / IN_REVIEW / APPROVED / REJECTED
3. 优先级：P0 / P1 / P2
4. 类型态：API / UI / PERFORMANCE

规则：

1. 颜色语义固定，不同页面不要变
2. 尽量胶囊化，不用纯文本堆信息
3. 强状态高对比，弱状态低对比

### 12.5 页头规范

页头统一成：

1. 左侧：标题 + 副标题
2. 右侧：1 个主操作 + 0-2 个次操作
3. 需要时可以挂一个摘要条或状态说明

避免：

1. 页头右侧出现太多按钮
2. 页头下面立刻又堆一行无区分度的工具栏

### 12.6 弹窗规范

复杂弹窗统一遵循：

1. 顶部：任务标题 + 简短说明
2. 中部：按业务结构分区
3. 底部：主操作固定在最右
4. 超复杂内容不要继续堆长表单，要有编辑器感或分块感

## 14. v1 边界说明

为了保证本轮能真实落地，必须明确边界。

### 14.1 本轮明确要做

1. 全局设计 token 扩充
2. 导航框架升级
3. 工作台重做
4. 接口用例编辑器视觉升级
5. 执行中心 / 报告中心结构优化

### 14.2 本轮明确不做

1. 不更换前端框架
2. 不替换 Element Plus 为全新组件库
3. 不先做整站 Figma 大稿再开发
4. 不做完整深色模式
5. 不一次性重写所有页面
6. 不把所有页面都改成完全不同的视觉风格
7. 不优先做炫酷动画和大面积装饰

### 14.3 范围控制原则

如果某个页面改造出现下面情况，应当停下来收口：

1. 需要大量新增后端接口才能完成
2. 需要重写整个交互模型
3. 会明显拖慢主流程页面的可用性
4. 只是为了“更好看”，但没有提升信息表达

## 15. v1.1 的执行建议

补完上述内容后，这份方案更适合作为开发执行稿。

推荐按下面方式推进：

1. 先做一轮全局基础层改造
2. 用工作台做第一张标杆页
3. 用接口用例编辑器做第二张标杆页
4. 再把执行中心和报告中心跟进统一

如果需要继续落地，下一步最合理的动作还是：

1. 直接开始改全局 token 与框架层
2. 做完后立刻接工作台
3. 再深改接口用例编辑器

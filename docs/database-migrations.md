# Database Migrations

The backend schema is versioned with Alembic. Application startup checks the
database revision; the backend container upgrades to `head` before starting
Uvicorn. A revision mismatch prevents the app from serving traffic.

From `backend/`, use:

```bash
python -m app.db_migrate check
python -m app.db_migrate upgrade
python -m app.db_migrate revision --message "describe schema change"
```

Review every autogenerated revision before deploying it. Data transformations,
constraints, indexes, and downgrade behavior may need explicit edits. Never use
`Base.metadata.create_all()` as a production schema migration.

## Existing Databases

An unversioned database is stamped with the baseline only when its existing
tables match the baseline schema. The bootstrap refuses to guess if the
`alembic_version` table is empty, the schema is incomplete, or it already
contains a post-baseline migration column. These checks are deliberate: inspect
the database and resolve its revision history before retrying; do not drop the
version table or alter business data to bypass the check.

The initial baseline is intentionally irreversible. Later revisions should
provide a reversible downgrade when that can be done without losing data. Test
upgrade and downgrade paths against disposable SQLite and MariaDB databases
before production rollout. Legacy project/environment variable pools are
encrypted by a data migration; `APP_ENCRYPTION_KEY` must be configured before
upgrading a database that still contains plaintext values.

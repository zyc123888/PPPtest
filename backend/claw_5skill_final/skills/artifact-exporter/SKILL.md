# artifact-exporter

## 角色

你是产物导出 Skill。

你的职责是把结构化产物整理成最终交付格式。

## 输入

你读取：

1. `TestcasePackage.yaml`
2. `ReviewReport.yaml`

## 目标产物

默认最终交付只保留一个文件：

1. `需求文档同名.xmind`

其余文件只作为内部中间产物或调试产物，可选保留，不属于默认对外交付：

1. `FunctionPoints.yaml`
2. `TestcasePackage.yaml`
3. `ReviewReport.yaml`
4. `需求文档同名.xmindmark`
5. `TestCases_Full.md`
6. `DeliverySummary.md`

**【极其重要：只能使用项目共用 exporter】**
业务 Skill 不能自行拼接 JSON/XML 或生成另一份临时 `.xmind`；必须使用项目内受测试的确定性 exporter，并校验实际交付归档。

你必须按照以下步骤生成最终导图：

1. 先生成符合规范的 `.xmindmark` 文件。
2. 再调用项目共用的确定性 exporter 生成最终 `.xmind` 文件。
3. 解析实际 `.xmind`，确认根节点非空且 TC 数量与用例包一致。
4. exporter 或实际文件校验失败时必须中止交付。

## 文件命名规则

最终交付的导图文件必须与原始需求文档保持同名，只替换扩展名。

例如：

1. 输入需求文档：`ADX Ad Block 支持HTML keyword 屏蔽.md`
2. 导图源文件：`ADX Ad Block 支持HTML keyword 屏蔽.xmindmark`
3. 最终交付文件：`ADX Ad Block 支持HTML keyword 屏蔽.xmind`

约束：

1. `.xmind` 是最终交付主文件，必须产出。
2. `.xmindmark` 是导图源文件，默认不对外交付。
3. 不要默认导出为 `TestCases.xmind`、`output.xmind` 这类通用名。
4. 如果输入不是 `.md`，则以需求主文件名或用户指定项目名作为导图基名。

## 最终交付规则

1. 默认对外只交付一个 `.xmind` 文件。
2. `.xmindmark`、Markdown 明细、Summary 都属于内部或调试产物。
3. 除非用户明确要求，否则不要在最终回复中枚举这些内部产物。
4. 不能因为生成了内部文件，就把它们误当成默认交付结果。

## 可选 Markdown 输出

只有在用户明确要求时，才额外输出 Markdown 明细：

至少包含：

1. 项目标题
2. 用例总数
3. 分场景展示
4. 每条用例的：
   - CaseID
   - 标题
   - 优先级
   - 前置条件
   - 测试数据
   - 步骤
   - 预期结果

## XMindMark 输出要求

导图是展示层，不是主事实源。

最终导图展示内容必须使用中文。

`xmindmark` 内容必须使用“根节点纯文本 + 子节点标准 Markdown 列表”的唯一格式，不要混用其他树表达方式。

原因：

1. 标题层级语法在实际导出 `.xmind` 时更容易出现层级扁平、标题文本混入节点内容的问题。
2. 混用“纯缩进文本”和“列表语法”会导致父子关系解析不稳定。
3. 经过实际导出验证，统一使用列表语法更适合本方案的测试用例导图。

唯一合法写法约束：

1. 第一行必须是根节点纯文本，不带 `- `。
2. 从第二行开始，每一行子节点都必须以 `- ` 开头。
3. 根节点的直属子节点必须顶格写 `- `，不能额外缩进。
4. 更深层子节点必须统一比父节点多 2 个空格缩进。
5. 禁止使用 Tab 缩进。
6. 禁止在主树中插入空行。
7. 禁止在主树中插入解释性文本、编号列表或普通段落。
8. 禁止使用纯缩进无 `- ` 的写法。
9. 禁止使用 `# / ## / ###` 标题层级语法。

整棵导图结构必须固定为：

1. 根节点：`项目名 + 测试用例`
2. 根节点下固定一个子节点：`统计信息`
3. 根节点下固定若干 `模块`
4. `模块` 下固定若干 `场景`
5. `场景` 下固定若干 `功能点`
6. `功能点` 下固定若干 `CaseID-标题`
7. `CaseID-标题` 下固定字段节点：`优先级：...｜类型：...`
8. `CaseID-标题` 下固定字段节点：`预期摘要：...`
9. `CaseID-标题` 下固定字段节点：`操作步骤`
10. `操作步骤` 下再展开：`步骤1` / `步骤2` / `步骤3 ...`

## 导图层级与字段映射

必须按下面映射输出：

1. 根节点
   - 取自 `project`
2. `统计信息`
   - 由导出阶段聚合生成
3. `模块`
   - 取自 `module`
4. `场景`
   - 取自 `scene`
5. `功能点`
   - 取自 `fp_id + "：" + title`
6. `CaseID-标题`
   - 取自 `case_id + "-" + title`
7. `优先级：...｜类型：...`
   - 由 `priority + "｜" + category` 组合生成
8. `预期摘要：...`
   - 取自 `expected_results` 的压缩摘要
9. `操作步骤`
   - 取自 `steps`
10. `步骤1：...`
   - 取自逐条步骤

## 展示字段中文映射

内部结构允许保留英文键名，但最终导图节点文案必须转成中文。

类型映射至少包含：

1. `functional` -> `功能`
2. `boundary` -> `边界`
3. `negative` -> `异常`
4. `decision_table` -> `决策表`
5. `state_transition` -> `状态转换`
6. `role_matrix` -> `角色权限`
7. `entry_consistency` -> `多入口一致性`
8. `pairwise` -> `组合测试`
9. `crud_lifecycle` -> `数据生命周期`
10. `idempotency` -> `幂等重试`
11. `data_consistency` -> `数据一致性`
12. `calculation_precision` -> `计算精度`
13. `batch_partial_failure` -> `批处理`
14. `observability_audit` -> `审计日志`

审查结论映射至少包含：

1. `pass` -> `通过`
2. `conditional_pass` -> `有条件通过`
3. `fail` -> `不通过`

## 统计信息节点要求

根节点下必须固定有一个 `统计信息` 节点，至少包含：

1. `功能点总数`
2. `用例总数`
3. `P0 数量`
4. `P1 数量`
5. `P2 数量`
6. `P3 数量`
7. `审查结论`

测试用例节点必须使用以下层级：

1. 测试用例主节点：
   - `CaseID-标题`
2. `CaseID-标题` 下至少包含：
   - `优先级：P0/P1/P2/P3｜类型：功能 / 边界 / 异常 / ...`
   - `预期摘要：...`
   - `操作步骤`
3. `操作步骤` 下再按步骤拆分子节点：
   - `步骤1：...`
   - `步骤2：...`
   - `步骤3：...`

输出时不允许再拆出单独的 `标题` 包装层，也不允许把所有信息塞进一个长文本节点。

## XMindMark 写法示例

```text
项目名测试用例
- 统计信息
  - 功能点总数：9
  - 用例总数：28
  - P0 数量：9
  - 审查结论：有条件通过
- 模块：后端过滤
  - 场景：Publisher 全局 HTML Keyword 过滤
    - FP-001：支持 HTML keyword 过滤规则
      - TC-001-001-新增规则正常保存
        - 优先级：P0｜类型：功能
        - 预期摘要：规则保存成功且列表正确展示
        - 操作步骤
          - 步骤1：进入功能页面
          - 步骤2：填写合法内容
          - 步骤3：点击保存
```

错误示例：

```text
- 项目名测试用例
  - 统计信息
    - 功能点总数：9
```

上面这种“根节点也带 `- `”的写法不允许使用。

## 模块与场景划分规则

1. 必须先按 `source_order` 保持需求文档原始分类和章节顺序
2. 在原文顺序内按 `module` 分组
3. 每个 `module` 下再按 `scene` 分组
4. 不能把所有功能点直接平铺在根节点下
5. 不能跳过 `scene` 层直接从 `module` 进入 `功能点`
6. 如果输入里没有显式模块名，允许分析阶段生成稳定模块名，但导出阶段不得自行再改名
7. `module` 和 `scene` 的名称、分组、顺序必须优先继承需求文档原始分类和章节顺序
8. 不允许为了“测试视角更清晰”而重新规划一套与需求文档顺序不同的模块结构
9. 图片、原型、补充说明产生的用例，应挂回最接近的需求文档原始模块下

## 功能点节点命名规则

功能点节点建议格式：

```text
FP-001：功能点名称
```

如果同一场景下存在多个功能点，不得省略 `fp_id`。

## 单个用例节点完整结构

```text
CaseID-标题
  ├─ 优先级：P1｜类型：功能
  ├─ 预期摘要：...
  └─ 操作步骤
      ├─ 步骤1：...
      ├─ 步骤2：...
      └─ 步骤3：...
```

## 导出排序规则

导出时必须按以下顺序稳定排序：

1. 先按 `source_order` 保留需求文档原始章节/分类顺序
2. 同一 `source_order` 下按 `module` 的首次出现顺序
3. 同一 `module` 下按 `scene` 的首次出现顺序
4. 同一 `scene` 下按 `fp_id` 顺序
5. 同一功能点下按 `case_id` 顺序

禁止行为：

1. 不允许按模块名称字母序重新排序
2. 不允许按优先级把 P0/P1 用例提前，打乱需求文档结构
3. 不允许把后端、前端、报表等模块按测试经验重新归类到新顺序
4. 不允许把原文靠后的章节提前到导图前部，除非需求文档本身就是这个顺序

## 交付摘要要求

只有在用户明确要求时，才额外输出交付摘要。

至少包含：

1. 功能点数量
2. 用例数量
3. 审查结论
4. 主要风险
5. 交付文件清单

## 禁止事项

- 不修改用例语义
- 不擅自调整优先级
- 不忽略审查结论
- 不使用 Python、Node.js 或其他脚本手动拼接 `.xmind` 压缩包
- 不在 `xmindmark` 命令缺失时退回到脚本拼装 `.xmind`
- 不把根节点写成列表项
- 不混用“纯缩进文本”和“标准 Markdown 列表”
- 不使用除 2 空格之外的其他缩进宽度
- 不在主树中插入空行或注释说明
- 不使用 `# / ## / ###` 标题层级语法表达 XMind 主树
- 不输出 7 层以上的深树结构
- 不把 `functional`、`boundary`、`negative`、`conditional_pass` 这类英文枚举直接展示给最终用户

## 成功标准

最终导出物应满足：

1. 默认只交付一个 `.xmind`
2. `.xmind` 人可读且可直接交付
3. `.xmind` 与结构化事实源一致
